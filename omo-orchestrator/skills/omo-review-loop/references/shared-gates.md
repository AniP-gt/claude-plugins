# Shared Reviewer Preamble and Gates

Paste this whole file into every lane prompt (inner lanes, the evidence gate, the Copilot prompt file, and the Phase 6 contract). These gates mirror the `review-pr` perspectives so the inner loop and the outer gate judge by the same rules.

## Common Preamble

1. **Independence**: judge from the diff, the codebase, and the supplied context only. Do not read other lanes' files in the iteration directory.
2. **Project rules first** (gate 17): load them before forming any finding.
3. **File understanding**: for each changed file, state its role in the system, the file-local change, and what it means for the whole task (use cases, data flow, transaction boundaries affected).
4. **Pre-finding verification**: when the diff alone leaves "is this intentional?" or "can this case occur?", check existing patterns in the same and related files, caller/callee and type constraints, tests, and design intent in comments or names. Matches an existing pattern -> do not flag (unless a written project rule forbids it, gate 17). Still an issue after checking -> flag and say it survived codebase verification. Cannot verify -> do not flag.
5. **Existence check**: before asking to add or change a file or setting not in the diff, confirm with Glob/Grep that it exists. Unverifiable -> do not flag.
6. **Output**: return the report in the lane's STRICT format. Findings cite `file:line` and concrete evidence. Write `(none)` under empty sections.

## Gates

1. **Domain scope filter**: review shipped product/domain behavior. Ignore incidental AI-harness, bot, generated-analysis, or review-tool noise unless the task changes that tooling.
2. **Existing behavior parity**: for calculations, data correction, persistence/update flows, callbacks, or batch/import behavior, compare with the existing source of truth: operands, units, rounding, nil/zero handling, derived fields, validations, transactions, callbacks, side effects, audit/history writes, dependent-record sync. Same, or an intentional difference backed by goal/tests/comments -> not a defect. Unexplained difference that can affect persisted data, money, quantities, inventory, reports, or user-visible state in normal operation -> blocking. No source of truth found after targeted search -> list the searched locations and keep it Needs Attention, not speculative Critical.
3. **Applicability and proportionality**: before reporting, prove (a) exact predicate match from the real arguments, query predicates, unique keys, flags, env guards, callbacks, or contracts; (b) a reachable normal-operation scenario; (c) no existing mitigation (callbacks, locks, idempotent queues, service contracts, operator workflow); (d) a proportionate fix. Theoretical or manual-only risks become Warnings or Notes unless normal operation can corrupt data, expose security, break a user flow, or create unrecoverable state. Exception: a manual script that can mutate production data without an explicit environment guard is still reported (Needs Attention).
4. **Match-set breadth**: state the full set of cases a condition matches, not only the targeted one. When a guard tests an attribute at a broader scope than the feature it gates (an org-level flag gating a store-level feature, a tenant column gating a per-user branch), enumerate the discriminator combinations it also admits and confirm the requirement intended each. A combination admitted but never named is Needs Attention with the combination spelled out. Guard clauses and early returns count: a guard placed first claims every case it matches.
5. **Verified non-issues**: a suspected issue or prior comment disproven by evidence goes to Notes with the disproving predicate or contract, never to Blocking or Warnings.
6. **Lifecycle**: for schedulers, recovery, alerts, admin/master data, imports, exports, and manual correction flows, model repeated execution cycles and downstream effects, not only the happy path.
7. **Comment quality and AI slop safety**: request comments only for non-obvious intent or domain relationships. Keep helpful explanatory comments. AI slop is minor unless repeated 5+ times or severe.
8. **Goal alignment**: completeness, constraints, over/under-implementation, edge cases, history, and description/doc accuracy.
9. **External library contract**: judge every changed path that depends on a third-party library against the recorded installed-version evidence, even with no dependency diff. Missing applicable evidence is blocking. Runtime-behavior assumptions need installed source, `--help`, or an execution log; docs alone are not evidence.
10. **Behavior change and intent disclosure**: when the diff changes anything an existing consumer can observe (query predicates, scopes, sorts, response shape, serializer keys, defaults, new caps or pagination, status codes, error shapes, enum/allowed values, or a claimed "pure refactor"), enumerate consumers by search, state before/after per consumer, and label each `documented+intended` / `documented but unjustified` / `undocumented` against the goal/spec. Record the comparison even when concluding "no behavior change". `undocumented` + reachable + removed data, truncated results, dropped fields, or changed stored/allowed values is blocking. `documented+intended` with a plausible rationale is a Note. Check both directions (spec claims X the code lacks; code does Y the spec never mentions). File one root cause once, under `behavior-change`.
11. **Documentation as claims**: when the diff changes a `.md`, runbook, design/spec doc, README, or behavior-describing comment block (including doc-only diffs), verify each production-behavior assertion against source with Read/Grep, never against the doc itself. Typo, format, and link fixes skip the audit (minor Nit); aspirational sections are exempt. Check association/schema, trigger, mechanism, config/routing claims, per-case tables, and internal consistency (ranges vs contents, legend completeness, cross-references, table vs prose). A doc misstating production behavior is Needs Attention at minimum, blocking when it is the operative reference for a risky procedure. A right conclusion through a wrong stated mechanism is still a finding. For large assertion sets, verify direction-changed assertions first and state the audit boundary.
12. **Disposable one-off scripts** (before any test-coverage finding): classify each file as production or disposable from evidence: outside the shipped tree, manual invocation, stated single use, no production caller. Two or more -> disposable: a missing test is at most a minor Nit, never blocking, and do not propose moving the logic into permanent code. Other gates apply more strictly; a script mutating production data without manual-verification evidence (dry run, staging run, row counts) is Needs Attention. Grade mixed diffs per file.
13. **Re-entry, sentinel state, alert cardinality**: for jobs, schedulers, locks, retries, recovery, or alerting, model more than one cycle. Can fragile work in a `rescue`/recovery path raise and skip cleanup, sentinel release, retry scheduling, or later records? Is every return path observable on the next tick? Do alerts fire once per state transition or repeatedly? Can another worker see an intermediate sentinel (`processing`, claim markers) and re-enter? Does a sentinel whose owner dies stay recoverable? For a fix to a race, duplicate alert, or stale lock, model the post-fix state machine and confirm the only self-healing path survives. Distinguish idempotent data convergence from duplicate external side effects; prefer targeted guards over broad transaction rewrites.
14. **Admin, master, and business data lifecycle**: input normalization across fields, encoding/export compatibility (SJIS, CSV, PDF, file names, external systems), propagation to dependent rows, caches, denormalized columns, reports, inventory, audit history, recalculation needs, duplicate or concurrent operations, the correction path for wrong operator input, tamper resistance via strong parameters and allowlists, related-table integrity, scheduled import versus manual edits, read-only/historical boundaries, and dev/staging-to-production assumptions. Reachable corruption of business data, inventory, reports, money, security boundaries, or a user flow is blocking; unclear but recoverable assumptions are Needs Attention.
15. **Validation callback and override parity (Rails forms and template methods)**: confirm the caller uses the return value (`false if errors[...]` is dead when discarded); compare old and new execution matrices so new guards do not skip a previously unconditional validation; confirm inherited existence, tenant/scope, and authorization checks still run or have a proven equivalent (a scoped finder is not automatically an authorization check); compare guard style across siblings; check client dependence on error keys or order. An override that can drop tenant, scope, authorization, or existence checks in normal operation is blocking unless equivalence is proven.
16. **Nits pass** (report-only, never affects the verdict): after Blocking and Warnings, list `Nit: high` (misleads maintainers: stale names or comments, generic names for feature-specific code, misleading test names), `Nit: medium` (local readability, small duplicated conditions, literals where a nearby constant exists), `Nit: low` (typos, formatting, wording). Escalate out of Nits when behavior, data, security, compatibility, tests, or user-visible output can change. Each Nit needs `file:line` and a tiny fix, or omit it.
17. **Project-specific rules** (first step, not a final cross-check): `ls .claude/rules/`, read each rule's frontmatter, map every changed file to the rule files whose `paths` globs match (broad globs like `**/*.vue` or `app/forms/**/*.rb` match more than they seem), and write that mapping out. Read matched rules in full, plus root `CLAUDE.md` / `AGENTS.md` with `@file` includes. Report matches and a violation count; at zero, state affirmatively that each matched clause was checked. A violated clause with a decision date or recorded rationale is blocking; an undated style clause is normally a Nit; a rule that states its own severity wins. Cite the rule path and clause. Widespread existing usage never excuses a rule violation. Before demanding an untouched generated file, lockfile, or schema dump, check `git ls-files`: an untracked or ignored file cannot be committed.
18. **Author-declared scope exclusions**: treat "out of scope" declarations as priority hints. Still read every changed file and report correctness, safety, and project-rule findings there; suppress only style and polish, saying so once in Notes. Exclusions never remove a file from goal-alignment or behavior-change analysis and never suppress a blocking finding.
19. **Prose readability and reachable references**: comments, YARD, docs, and spec descriptions state facts plainly in the project's language. Flag coined literal translations, metaphors or personification, direction-only framing, bare English words in otherwise Japanese prose, and narration of how internals were verified; do not flag domain terms tied to the issue or class names or words already common in the repo (`git grep -c`). Flag references to untracked or ignored paths and to section IDs of untracked memos (`git ls-files`; `git diff | grep -nE 'docs/issues|docs/guidelines|tmp/|\.claude/'`). Unreachable references are blocking when a project rule bans them, otherwise Warning.
20. **New component readiness** (new job, scheduler entry, or query object): responsibility-placement rationale, a stop procedure for any manual operation being replaced, query objects with an SQL `@example`, a dedicated spec, and EXPLAIN, a Mermaid diagram with independently triggered flows separated, and explainable failure paths (including `ensure` cleanup that can raise). Warning unless a project rule says otherwise. With no PR body in the loop, PR-body items go to Notes as "include when the PR is written". A new scheduler entry's run time must be checked against the scheduler config (for example `config/sidekiq.yml`) for collisions with jobs touching the same tables, in full.
21. **Caller-to-callee argument wiring**: when a caller passes a new or changed argument into a job or service (`perform_now`, `perform_later`, method call), a passing callee spec proves nothing about the caller. Require the caller's spec to assert the value (`have_received(...).with(...)`), stubbing call-site-nil values (for example `provider_job_id` under `perform_now`) to non-nil so "wired" and "always nil" differ. A missing caller-side assertion for a changed wiring path is blocking.
22. **Spec and signature granularity**: (a) an optional or nil-default argument, or nil-only branch, no production caller uses (grep callers outside `spec/`); (b) one example triggering several branches and asserting once at the end, especially with a negative assertion; (c) the same stub set repeated across example groups instead of a file-local `shared_context`. All pass CI, so green is not evidence. Report (a) and (b) as `Nit: high`, (c) as `Nit: medium`, blocking only when a project rule says so.
