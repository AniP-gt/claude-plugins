# OMO Implement

Use this skill for one scoped implementation or fix pass after scope is concrete. When delegated, return the result to the caller's active Ralph controller; do not start another controller or review loop. When invoked standalone and not escalated to ultrawork (below), initialize or reuse `omo-ralph-loop` for this task. Ralph's final gate (an omo reviewer, review-only `self-review`, and the Codex lane) reviews the change before the task completes, a one-file fix included; `REQUEST_CHANGES` starts the next fix pass, whose result is reviewed again, until the gate returns `APPROVE` or Ralph stops. That gate is the review: do not also run `/omo-review` per pass.

Plan first: when invoked standalone with no approved `omo-plan` for this change, run `omo-plan` before editing. Skip it only when the whole change is a typo fix, a wording change, or a config value change; documentation changes are not exempt. Skip the check when an active controller delegated this skill.

Load `omo-guardrails` with the Skill tool before the first dispatch or edit; other sections cite its rules by name only. Every dispatch to `omo-researcher`, `omo-reviewer`, `omo-implementer`, or `omo-planner` carries a `LOAD_SKILLS` line chosen from `omo-orchestrate` `references/skill-catalog.md` (`LOAD_SKILLS: none` when no row applies); a PreToolUse hook denies it otherwise.

Ultrawork escalation: when invoked standalone, size the task first and decide whether to enter ultrawork by the `omo-ultrawork` skill's `references/auto-escalation.md`. Skip the check when an active controller delegated this skill.

## Steps

1. Read the relevant code and nearby patterns. When the task comes from an older issue or one phase of a staged plan, first check that its premise still holds: another change already did it, the framework's default behavior already covers it (a queue that requeues on graceful stop), or a cheaper means exists. If any holds, report it with evidence and ask before implementing.
   - Repeated notifications: check three conditions. (1) The change adds or changes a notification (an error tracker, pager, chat, email). (2) A job or retry that runs more than once a day can send it again while the same condition persists; a missing setting or credential checked on every run counts. (3) The request does not say how often a person must hear about it. When all three hold, do not pick the frequency yourself, even a guarded one; restricting it to some environments is part of the same question.
   - Ask the user before implementing that part. Give the per-day count, its cost (tracker quota or billing, noise that hides other alerts), the options with what each changes (every occurrence, once per state change, once per day, log only), and your recommendation.
   - Parts that do not depend on the answer may proceed meanwhile. When none exist, stop and ask now, before the ultrawork sizing and the Ralph loop setup, and write no skeleton; the read-only exploration that confirmed the three conditions is fine.
   - A notification sent once per user action, once per state transition, or from a job that runs once a day or less often needs no question; implement it directly.
   - Notification text: put the target ID and the specific cause in the message string itself, not only in the structured fields or extra data the helper takes, because a chat line or tracker title may show only the string. When several conditions share one notification, name the one that fired; when a whole run fails, include the run's arguments. When a project rule states what more it must show, follow it. When neither the rule nor the request says what more it must show (impact, recovery steps, a docs link) or in which language, implement the ID and cause now and ask the user with one draft message per notification before adding more.
2. Confirm the smallest behavior change that satisfies the request. When it modifies existing code, build the risk map described in `/omo-review` (Review Areas, risk map) before editing, as a short list with one line per modified unit: visible callers with the search used, hidden reach for each `/omo-review` category (found, none, or could not verify; within that unit's line, the categories marked none may be grouped in one phrase), its guardrail, and business impact. Treat rows with business impact and no guardrail as places that need a test or an explicit check. For each risk, say whether it already exists or this change introduces it, and its trigger and frequency (every deploy, only on crash). When the change targets a failure path (a crash, OOM, timeout), also state its effect on the routine path (normal deploys, restarts, daytime traffic) before editing; a lock that is now reclaimed only after a TTL can stall a latency-sensitive job on every deploy. Evaluate it both on the current code and after any change already planned for the same path (a cleanup hook another issue will remove), and say which of the two each effect belongs to.
3. Decide test necessity from the change scale. Tests are required when the change adds or changes branching logic, a calculation, a state transition, a data write, parsing or validation, a public contract, or fixes a bug (the regression test must fail without the fix). When tests are required, design the cases with `/omo-test-design` when more than a single regression case is needed (tell it to write directly and return the case table, since it otherwise waits for approval), then work test-first: write the test, run it, confirm it fails for the expected reason, then implement until it passes. When tests are not required (wording, including only the text of an existing message, docs, renames, config values, wiring that adds no branch; a rename or text change needs a test only when an in-repo consumer matches on the old name or text (a lookup by string, a caller comparing an error message); an outside consumer that could not be verified is reported as unverified, not a reason to add a test), skip TDD and name the diagnostic or real-surface check that proves the change instead.
   - Before writing any test or code, design the real-surface QA and get `APPROVE` on it by `references/real-surface-qa.md` (Design and Review). Every change gets at least one real-surface scenario, sized to the diff.
4. Edit only the required files.
5. Record evidence for the diff: changed files, affected callers, and the validation target that proves the change. For every pre-existing dirty file, record whether it is in scope and the observed status or diff evidence that it was not modified by this work.
6. Run diagnostics on changed files.
7. Run targeted tests, then broader checks if warranted, then the approved QA design by `references/real-surface-qa.md` (Run, Tool Selection); steps 4 through 7 are one continuous flow with no report in between. The real deliverable surface is a live HTTP request for an API (`curl` against the local server), a real CLI/TUI session, a real browser interaction, an import-and-use driver for a library, or the resulting artifact for data-shaped work. For a background job, the surface is the job run by a real worker process with its real queue and lock store; a test that calls it inline does not count. When the change touches the job's code path (its loop or control flow, error handling, retries, or locking, including those parts inside services it calls; not a pure formatting or value helper), include these even if the lock and shutdown code are unchanged, because an interruption mid-run lands in the changed code: a graceful stop in mid-run with the production timeout (what a rolling deploy sends) and a hard kill in mid-run (what an OOM kill does), each followed by the re-run, while the inputs the job normally receives keep arriving. Do this before reporting the change done, without waiting to be asked.
8. When a required diagnostic, test, or real-surface check is unavailable, report the exact unverified area and why it is unavailable. Do not claim completion or approval until equivalent evidence is obtained or the blocker is explicitly handed off.
9. Return changed files, validation results, evidence, and any unverified area to the controller. Every remaining issue or open decision in the return names the code read for it (`path:line` of the body that would misbehave); one inferred from a name, a schedule entry, or a similar component is read first or labeled an unverified guess (see `omo-guardrails`). Every change is reviewed, a one-file fix included: by the active controller's final gate (Ralph, ultrawork, or the `omo-review` mode `review-loop` lanes), or by `/omo-review` when no controller is active. Never both.
10. Verify supplied findings against current code, tests, or a stated contract. Record unconfirmed findings as unconfirmed. A fix pass applies the confirmed scoped directives, validates them, and returns; it never dispatches another fix pass.
11. Further repair and re-review require the next iteration of the same Ralph ledger and budget. Report blocking findings and evidence to the controller; do not claim task completion before its independent final `APPROVE`.

## Hard Rules

- Do not use `as any`, `@ts-ignore`, or `@ts-expect-error` to suppress errors.
- Do not delete or weaken tests to pass.
- Do not add fallback or legacy paths unless required by an existing external contract.
- Do not modify unrelated dirty files.
- When a new small type or helper exists only to satisfy another component's interface (a placeholder passed instead of a record, an adapter), give it a short comment saying why it exists and naming one caller; its own file does not show how to use it. When a new job or service works on the same records as an existing one (two monitors of the same state), comment the division of roles in both.
- Do not ask the user to push or open a PR while the change has not passed its review (step 9); run the review first, then report.
- Do not state a lock hold time, run time, or failure-path outcome in comments, docs, or the change description unless a measurement or test backs it; otherwise label it an estimate.
- Do not treat review as advisory when a finding is confirmed and blocking.
- Do not claim a check passed unless you ran it in the current session.
- Report discovered work outside the assigned scope to the coordinator. Do not fix it until it is recorded, scoped, dependency-checked, and dispatched as required work.
